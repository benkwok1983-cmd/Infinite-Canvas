\- 项目：Infinite Canvas

\- 校审对象：Zcode 分支 `zcode/iteration-01`

\- 重点提交：`91e9b8e`

\- 校审边界：未修改 Zcode 项目代码、配置或其他项目文件



本报告是在第一次代码校审基础上，对 Zcode 针对六项问题提交的修复进行二次复核。



\## 二、总体结论



提交 `91e9b8e` 已落实第一次校审提出的主要修复方向，包括：



\- 删除可能泄露 API Key 的完整命令行日志；

\- 持久化 API 回退开关；

\- 扩充 Skill 编译缓存键；

\- 允许 Skill 驱动的空提示词生图；

\- 补充预览参数；

\- 为 Skill 覆盖安装增加失败回滚；

\- 增加缓存临时文件写入、`SKILL.md` 大小限制及相关回归测试。



整体修复方向正确，代码的安全性与可用性已有明显改善。



但是，本轮复核仍发现：



\- 1 项 P1 高优先级测试隔离问题；

\- 3 项 P2 中优先级实现缺陷；

\- 测试数量、CI 状态和服务重启情况缺乏可独立核验的证据。



因此，当前版本适合继续在独立分支测试，不建议未经后续修复和验收便直接合并到正在使用的稳定分支。



\## 三、已确认完成的修复



\### 1. API Key 日志泄露风险已处理



原先可能输出完整启动参数 `argv` 的调试日志已被删除。



该修改能够避免启用 API 回退后，真实 API Key 随完整命令行参数进入服务日志。



结论：修复方向正确，第一次校审提出的敏感信息泄露风险已经得到处理。



\### 2. `allow\_api\_fallback` 保存链路已补齐



前端 `saveProviders` 提交体已经包含：



```text

allow\_api\_fallback

```



这使得用户在界面中设置“API 回退”后，该设置能够随 Provider 配置一起提交给后端。



Zcode 同时增加了 PUT→GET 往返测试，用于检查保存后重新读取时，该字段是否仍然保持。



结论：业务缺口已经补齐。



但新增回归测试存在修改真实用户配置的风险，详见后文 P1 问题。



\### 3. Skill 编译缓存键已扩充



缓存键已经同时纳入：



\- 用户原始选择的 variant；

\- 解析后的 variant 标识；

\- variant 对应的模板或指令内容；

\- 其他原有的 Skill 编译输入。



这可以避免用户从样板 A 切换到样板 B 后，错误命中样板 A 的缓存。



结论：此前“切换样板仍复用旧缓存”的核心问题已经修复。



\### 4. API 生图支持 Skill 驱动的空提示词



请求模型已经允许 `prompt` 为空。



业务层校验改为以下三个条件至少满足一个：



1\. 存在用户提示词；

2\. 选择了 Skill；

3\. 存在参考图。



因此：



\- 只有 Skill、没有手工提示词时，可以继续生成；

\- 参考图加 Skill、没有手工提示词时，可以继续生成；

\- 提示词、Skill、参考图全部为空时，仍会被拒绝。



结论：符合“参考图 + Skill”以及“仅由 Skill 编译驱动”的实际需求，同时没有放开完全空白的无效生成请求。



\### 5. `SKILL.md` 文件大小限制已增加



Skill 安装和读取流程增加了 `SKILL.md` 最大 1MB 的限制。



这可以降低异常大文件造成以下风险的概率：



\- 内存占用过高；

\- Prompt 编译输入异常膨胀；

\- 恶意或错误仓库导致服务处理压力增加；

\- 不必要的大文件进入 Skill 系统。



结论：处理合理。



\### 6. Skill 覆盖安装增加了移动失败回滚



GitHub 安装和 zip 安装两条路径已经接入共用替换 helper。



当前流程大致为：



1\. 将原 Skill 目录改名为备份目录；

2\. 将新 Skill 移入目标位置；

3\. 如果移动新目录失败，尝试恢复原目录。



这比原来的“先删除旧目录，再移动新目录”明显更安全。



结论：移动阶段的回滚已经实现。



但是，当前事务范围还没有覆盖后续的元数据写入，详见后文 P2 问题。



\### 7. 预览请求前端已携带 variant 和 model



前端预览请求已经发送：



\- `variant`

\- `model`



这为“预览结果与实际生成结果采用相同样板和模型”提供了必要输入。



结论：前端部分已经完成。



但后端没有完整接收和使用 `model` 等参数，因此端到端问题尚未完全解决，详见后文 P2 问题。



\### 8. 缓存写入已使用临时文件和 `os.replace`



Skill 编译缓存不再直接覆盖正式缓存文件，而是先写临时文件，再通过 `os.replace` 替换。



这能够降低进程中途退出或写入失败导致正式缓存文件只写入一半的风险。



结论：单次写入的文件完整性有所改善。



不过当前实现仍有跨缓存 key 的并发竞争，不能视为完整的并发安全原子写，详见后文 P2 问题。



\## 四、仍需修复的问题



\### P1：回归测试可能修改用户真实 Provider 配置



涉及位置：



```text

tests/test\_skill\_library.py

```



涉及测试：



```text

test\_allow\_api\_fallback\_put\_get\_roundtrip

```



大约位于该文件第 287 行附近。



\#### 问题说明



该测试通过真实 `/api/providers` 接口读取和写入 Provider 配置。



测试结束时，又把 Codex Provider 的：



```text

allow\_api\_fallback

```



强制设置为 `False`。



这并不等同于恢复测试前状态，因为用户测试前的真实值可能本来就是 `True`。



此外，如果测试执行到一半发生异常，恢复步骤可能根本不会执行，导致用户当前正在使用的 Provider 配置被测试永久改变。



这种测试属于典型的测试环境隔离不足。



\#### 潜在影响



\- 用户原本开启的 API 回退可能被测试关闭；

\- 测试可能重写真实 Provider 配置文件；

\- 测试失败后无法保证恢复；

\- 用户可能直到实际生图失败时才发现配置被改动；

\- 自动化 CI 或重复测试可能持续污染运行环境。



\#### 修复建议



首选方案：



1\. 为测试创建临时目录；

2\. 使用 monkeypatch 将 `API\_PROVIDERS\_FILE` 指向临时配置文件；

3\. 在临时文件中完成 PUT→GET 往返验证；

4\. 测试结束后由测试框架自动清理临时目录。



如果由于架构原因必须测试真实路径，则至少需要：



1\. 在测试前保存原配置文件的完整原始字节；

2\. 使用 `try/finally` 保证恢复一定执行；

3\. 在 `finally` 中按原始字节完整恢复；

4\. 检查恢复写入是否成功；

5\. 不能假设原始 `allow\_api\_fallback` 一定为 `False`。



优先级：P1。



建议在再次运行完整测试套件之前先修复。

\### P2：缓存“原子写”仍存在跨 key 并发竞争



涉及位置：



```text

main.py

```



大约位于第 20211 行附近的 Skill 编译缓存写入逻辑。



\#### 问题说明



当前缓存写入采用固定的临时文件名，形式类似：



```text

SKILL\_COMPILE\_CACHE\_FILE + ".tmp"

```



但是，缓存锁是按照缓存 key 分离的。



这意味着：



\- 请求 A 使用缓存 key A；

\- 请求 B 使用缓存 key B；

\- 两者持有不同的锁；

\- 两者可以同时写入同一个 `.tmp` 文件。



可能出现以下执行顺序：



1\. 请求 A 读取正式缓存；

2\. 请求 B 读取正式缓存；

3\. 请求 A 写入固定 `.tmp` 文件；

4\. 请求 B 覆盖同一个 `.tmp` 文件；

5\. 请求 A 执行 `os.replace`；

6\. 请求 B 再执行 `os.replace` 时发现临时文件已不存在，或者替换了不完整内容。



即使两个替换操作均未显式报错，也可能因为双方都基于旧缓存读取并分别写回，造成部分缓存记录丢失。



如果异常被上层吞掉，该问题还会表现为偶发缓存失效，很难定位。



\#### 修复建议



1\. 为整个缓存文件增加文件级或进程级全局锁。

2\. 在同一把锁内完成完整流程：



```text

读取正式缓存

→ 合并本次记录

→ 写唯一临时文件

→ flush

→ fsync

→ os.replace

```



3\. 不要使用固定 `.tmp` 文件名。

4\. 使用同目录唯一临时文件，例如：



```python

tempfile.NamedTemporaryFile(

&#x20;   mode="w",

&#x20;   delete=False,

&#x20;   dir=cache\_directory,

&#x20;   encoding="utf-8",

)

```



5\. 临时文件必须位于正式缓存文件同一磁盘或同一目录，以保持 `os.replace` 的原子替换语义。

6\. 写入后执行：



```python

flush()

os.fsync()

```



7\. 如果替换失败，应清理遗留临时文件并保留可诊断日志。



优先级：P2。

\### P2：预览请求发送了 model，但后端丢弃该字段



涉及位置：



```text

static/js/canvas.js

```



大约第 8534 行附近。



后端涉及：



```text

SkillPreviewRequest

api\_skill\_compile\_prompt

```



大约位于 `main.py` 第 20336 行附近。



\#### 问题说明



前端已经在预览请求中发送：



\- `variant`

\- `model`



但是，后端 `SkillPreviewRequest` 没有完整声明和接收：



\- `model`

\- `provider`



后端创建 `SkillSelection` 时，也没有完整传递这些字段。



因此，前端虽然发送了 `model`，后端实际编译 Skill Prompt 时仍可能不知道用户将要使用哪个模型。



结果是：



\- 预览可能按照默认模型进行 Skill 编译；

\- 实际生成可能使用用户选定模型；

\- Skill 中如果存在按模型区分的编译规则，预览结果和实际生成结果仍可能不一致。



另外，旧的快速预览接口：



```text

/api/skills/preview-prompt

```



仍然直接调用快速 Prompt 组合逻辑，没有完整解析并传递 variant。



\#### 修复建议



1\. 在 `SkillPreviewRequest` 中明确增加：



```text

model

provider

```



2\. 构造 `SkillSelection` 时完整传入：



```text

skill\_id

variant

model

provider

```



3\. 让快速预览和智能预览共用同一套 variant 解析函数。

4\. 避免两套预览接口各自解释 variant，长期产生行为差异。

5\. 增加端到端测试，验证：



```text

预览使用的 Skill

预览使用的 variant

预览使用的 model

预览使用的 provider

```



与实际生成请求完全一致。



优先级：P2。

\### P2：覆盖安装事务未覆盖元数据写入



涉及位置：



```text

main.py

```



函数：



```text

swap\_staged\_into\_target

```



大约位于第 19940 行附近及其调用方。



\#### 问题说明



当前 helper 的注释和设计意图是：



\- 旧 Skill 先改名备份；

\- 新 Skill 移入；

\- 后续操作成功后再删除备份；

\- 失败则恢复旧 Skill。



但实际实现中，新目录移动成功后，旧目录备份很快就被删除。



调用方随后才写入：



```text

.skill\_meta.json

```



如果元数据写入失败，会出现：



\- 新 Skill 目录已经替换成功；

\- 旧 Skill 备份已经删除；

\- 新 Skill 的元数据没有成功写入；

\- 系统无法恢复旧 Skill；

\- 安装结果处于不完整状态。



因此，当前实现只保证“目录移动阶段”的回滚，并没有覆盖完整的 Skill 安装事务。



\#### 修复建议



方案一：把元数据写入纳入 helper。



完整流程应为：



```text

备份旧目录

→ 移入新目录

→ 写入元数据

→ 验证元数据

→ 删除备份

```



任何一步失败时：



```text

删除不完整的新目录

→ 恢复旧目录

```



方案二：helper 返回事务句柄。



例如：



\- `prepare\_swap()`：备份并移动新目录；

\- `commit()`：确认元数据成功后删除备份；

\- `rollback()`：删除新目录并恢复旧目录。



调用方只有在 `.skill\_meta.json` 写入成功后才能调用 `commit()`。



还应分别增加以下回归测试：



1\. GitHub 安装时元数据写入失败；

2\. zip 安装时元数据写入失败；

3\. 确认失败后旧 Skill 内容恢复；

4\. 确认失败后没有残留不完整的新目录；

5\. 确认备份目录得到正确清理。



优先级：P2。



\## 五、测试与验证结论




但是，按当前测试文件中的测试方法进行静态统计，数量为：




\- 使用了参数化测试；

因此，不能只依赖手工统计判断测试总数。



建议总结文档附上：



1\. 实际执行的测试命令；

2\. 测试框架的原始最终摘要；

3\. 通过、失败、跳过数量；

4\. 测试运行对应的提交编号；

5\. 必要时附测试日志文件。



例如应保留类似以下可核验信息：



```text

OK

```



或者 pytest 的：



```text

XX passed, XX skipped in XX.XXs

```

\## 六、代码层面的后续优化建议



以下项目不是本轮合并的首要阻断项，可以在功能稳定后单独处理。



\### 1. 拆分体积过大的 `main.py`



建议逐步拆分为：



```text

skill\_library.py

skill\_compiler.py

codex\_image.py

```



可能的职责划分：



\- `skill\_library.py`：Skill 安装、覆盖、元数据、目录管理；

\- `skill\_compiler.py`：Skill Prompt 编译、variant 解析、缓存；

\- `codex\_image.py`：Codex CLI 生图、API 回退、命令参数与结果处理。



建议在当前功能修复稳定后单独实施，不要和紧急 Bug 修复混在同一提交中。



\### 2. 控制 `SKILL\_COMPILE\_LOCKS` 生命周期



如果 `SKILL\_COMPILE\_LOCKS` 按缓存 key 持续增加且不清理，长时间运行后可能不断保留已经不再使用的锁对象。



可考虑：



\- 使用有限容量结构；

\- 在请求结束后安全移除无等待者的锁；

\- 直接使用文件级缓存锁，减少大量 key 锁的必要性。



该项优先级低于缓存文件并发写问题。



\### 3. 建立专门的 Skill 安装事务测试组



建议覆盖：



\- 新安装成功；

\- 覆盖安装成功；

\- 新目录移动失败；

\- 元数据写入失败；

\- 备份恢复失败；

\- 非法 zip；

\- 超大 `SKILL.md`；

\- GitHub 下载中断；

\- 安装完成后的元数据一致性。



\### 4. 建立预览与实际生成一致性测试



对于同一次选择，应验证预览和实际生成使用完全一致的：



\- Skill；

\- variant；

\- model；

\- provider；

\- 用户提示词；

\- 参考图信息；

\- 编译模式。



\### 5. 在 CI 中增加敏感信息检查



除常规测试外，可以增加以下检查：



\- 日志中不得出现完整 API Key；

\- 不得输出完整带密钥的命令行参数；

\- 测试不得访问真实用户配置；

\- 安装失败后不得留下半安装目录。
